PARA EMPEZAR · QUÉ ES SONARQUBE

Un revisor automático para cada cambio de código

SonarQube analiza el código fuente con reglas por lenguaje y señala los problemas antes de que un cambio se integre a la rama principal. Existe como servicio en la nube (SonarQube Cloud) o instalado en servidores propios (SonarQube Server).

QUÉ REVISA

Confiabilidad

Defectos que pueden hacer fallar el sistema en ejecución.

Seguridad

Vulnerabilidades, y código sensible (security hotspots) que Sonar marca para que el equipo lo revise.

Mantenibilidad

Código difícil de entender o de cambiar, y código duplicado.

Cobertura

Qué parte del código recorren las pruebas unitarias, medida cuando el pipeline las ejecuta.

CÓMO APORTA A LA CALIDAD

Perfil de reglas · Quality Profile

Qué reglas se aplican en cada lenguaje. Se define una vez y queda por defecto para todos los proyectos.

Filtro de calidad · Quality Gate

Los umbrales que un cambio debe cumplir. El resultado es uno solo: aprobado o fallido.

Foco en el código nuevo

Se exige a lo nuevo o modificado: la calidad mejora con cada cambio, sin frenar por lo existente.

En el día a día: el resultado aparece en el propio cambio de código en GitHub, con el detalle de cada problema. Lo que no hace: no reemplaza la revisión de una persona ni las pruebas funcionales; no sabe si el código hace lo que el negocio necesita. Documentación oficial: docs.sonarsource.com/sonarqube-cloud

PARA EMPEZAR · EL POTENCIAL DE SONAR

Lo que Sonar puede medir, del plan base al completo

VIENE CON SONARQUBE CLOUD

Calidad y seguridad del código propio

  • SAST: revisa el código fuente sin ejecutarlo. Detecta inyección SQL, cross-site scripting, deserialización insegura y más, con reglas mapeadas a OWASP Top 10 para C#.
  • Secretos: credenciales, llaves y tokens escritos en el código.
  • Infraestructura como código: Terraform, Docker, Kubernetes, CloudFormation, Ansible y workflows de GitHub Actions.
  • Confiabilidad, mantenibilidad y duplicación.
  • Cobertura de pruebas: de líneas y de condiciones, a partir de las pruebas que ejecuta el pipeline.
CON ADVANCED SECURITY

Seguridad de las dependencias

  • SCA: vulnerabilidades conocidas (CVE) en las librerías de terceros, priorizando las que el código realmente usa.
  • Paquetes maliciosos entre las dependencias.
  • Licencias: políticas de licencias permitidas.
  • SBOM: inventario exportable de todas las dependencias.
  • SAST avanzado: vulnerabilidades que nacen de la interacción entre el código y las librerías open source; disponible para C#/.NET.
CON PLAN ENTERPRISE

Reportes frente a estándares de seguridad

  • Reportes de cumplimiento: qué hallazgos de cada proyecto incumplen estándares como OWASP Top 10, CWE Top 25 o PCI DSS, el estándar de seguridad para pagos con tarjeta. Listos para el área de seguridad.
  • Una sola vista: todos los proyectos de Viva juntos, aunque estén en distintas organizaciones de GitHub.
Lo que no hace: no ejecuta la aplicación, así que no es DAST, IAST ni prueba de penetración; esas pruebas se hacen con otras herramientas. En este servicio configuramos las reglas .NET y el filtro de calidad; secretos e infraestructura como código ya vienen con SonarQube Cloud, y Advanced Security y el plan Enterprise se suman cuando Viva lo decida. Planes en la documentación oficial.

ESTADO ACTUAL

El equipo de desarrollo de Generic API no tiene acceso a la herramienta de calidad

DÓNDE ESTÁ

En la infraestructura de un tercero

La herramienta de calidad, SonarQube, vive en sonarqube.ezyflight.se: un dominio de Ezy, administrado por Ezy. Cada cambio de código enlaza ahí (por ejemplo, #2511).

QUÉ VE EL EQUIPO

Solo un semáforo y un número

El equipo de desarrollo de Generic API no tiene acceso: ve si el cambio pasó el filtro de calidad y cuántos problemas tiene, pero no cuáles ni dónde están.

QUÉ IMPLICA

Se desaprovecha la herramienta

Lo que no se ve, no se corrige. Y cualquier cambio de reglas o de accesos depende de pedírselo a un tercero.

Además, la revisión automática actual de Generic API no ejecuta las pruebas unitarias ni bloquea: un cambio con problemas detectados puede llegar igual a la rama principal.

Filtro de calidad

¿Cumple el estándar de Viva? Si cumple, pasa a la revisión de una persona; si no, no se puede integrar.

BLOQUEA
Propuesta inicial
del filtro
Pruebas unitarias que recorran al menos el 80 % del código nuevo · ningún defecto ni vulnerabilidad nueva · problemas de mantenimiento dentro del límite acordado · poco código duplicado (≤ 3 %).
Solo se exige al código nuevo de cada cambio: el código existente no frena el trabajo. Es el punto de partida: Viva aprueba los umbrales. Como hoy la cobertura no se mide, recomendamos que solo informe las primeras semanas y que Viva decida cuándo pasa a bloquear. Quedan como filtro por defecto para todos sus proyectos.

BENEFICIOS

Menos retrabajo, menos riesgo, más control

Viva Aerobus

  • Ningún cambio llega a la rama principal sin pasar el filtro, salvo un salto de emergencia autorizado por Viva.
  • Los problemas dejan de acumularse: se controla lo nuevo sin frenar por lo existente.
  • Cambia reglas y da accesos sin pedírselo a un tercero.
  • Si cambia un proveedor, el control de calidad y el historial que se genere desde ahora se quedan en Viva.

Revisores

  • Dejan de corregir a mano lo que una máquina detecta.
  • Dedican su tiempo a diseño y negocio.
  • Un solo criterio de calidad, igual para todos los cambios.

Equipo de desarrollo

  • Ve cada problema y dónde está, desde el propio cambio.
  • Sabe si su cambio cumple antes de que lo revise una persona.
  • Menos devoluciones y menos idas y vueltas por cambio.

PRECONDICIONES PARA PRESTAR EL SERVICIO

Lo que Viva decide y habilita

SONAR

En SonarQube Cloud

  • Aprobación de seguridad para analizar su código en la nube.
  • La organización de Viva, con plan Team o superior (lo contrata Viva) y un administrador para Tech and Solve.
  • Lectura del Sonar de Ezy para exportar las reglas y el filtro actuales; sin ella, partimos del perfil recomendado por Sonar (Sonar way).
  • La lista de equipos y personas con acceso, y su rol.
GITHUB

En GitHub

  • Administración del repositorio de Generic API: workflows, secretos y reglas de protección de ramas.
  • La app de SonarQube Cloud instalada en la organización de GitHub de Generic API, hoy de Ezy.
  • Permiso para integrar el cambio del pipeline en Generic API.
  • Un repositorio de prueba para la guía y el bloqueo.
DECISIONES

Lo que Viva decide

  • Un responsable con disponibilidad para aprobar reglas y filtro en las dos primeras semanas.
  • Qué ramas se protegen: master y las que indique.
  • Quién puede saltarse el bloqueo en una emergencia.
  • Que Generic API se analice solo en el Sonar de Viva.
  • Que corregir hallazgos y escribir pruebas sea parte de cada tarea.
SI ELIGE SONAR PROPIO

En su infraestructura

  • El servidor o la cuenta de nube, con acceso de administración.
  • El dominio, el certificado y la licencia Developer o superior, ya comprada.
  • Sonar alcanzable desde GitHub Actions: publicado en internet o con runners propios en la red de Viva.
  • Permiso para crear la GitHub App de Sonar en la organización de Generic API.
  • Viva opera el servidor después de la entrega.
Supuestos: todos los accesos y permisos, incluidos los que dependen de Ezy, se entregan antes de arrancar; los días hábiles cuentan desde ese momento. El pipeline se integra solo en Generic API; otros proyectos se suman con la guía o se cotizan aparte. Si una prueba unitaria no corre en el pipeline, se documenta y el bloqueo se activa con las que sí corren. No incluye corregir hallazgos existentes ni escribir pruebas unitarias.
