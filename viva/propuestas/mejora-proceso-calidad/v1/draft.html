ESTADO ACTUAL

El equipo de desarrollo de Generic API no tiene acceso a la herramienta de calidad

DÓNDE ESTÁ

En la infraestructura de un tercero

La herramienta de calidad, SonarQube, vive en sonarqube.ezyflight.se: un dominio de Ezy, administrado por Ezy. Cada cambio de código enlaza ahí (por ejemplo, #2511).

QUÉ VE EL EQUIPO

Solo un semáforo y un número

El equipo de desarrollo de Generic API no tiene acceso: ve si el cambio pasó el filtro de calidad y cuántos problemas tiene, pero no cuáles ni dónde están.

QUÉ IMPLICA

Se desaprovecha la herramienta

Lo que no se ve, no se corrige. Y cualquier cambio de reglas o de accesos depende de pedírselo a un tercero.

Además, la revisión automática actual de Generic API no ejecuta las pruebas unitarias ni bloquea: un cambio con problemas detectados puede llegar igual a la rama principal.

Viva, dueña de cómo se mide la calidad de todos sus proyectos

Las reglas de calidad dependen del lenguaje de programación, no del proyecto. Viva las define una vez y se aplican a todos sus proyectos.

Las reglas de calidad de Viva

LA PROPUESTA · PASO 1

Una herramienta de calidad de Viva, sin depender de un tercero

Viva tiene su propio SonarQube, con acceso para los equipos que Viva decida.

Propiedad

El historial de calidad del código de Viva queda en manos de Viva.

Accesos

Viva da y quita accesos cuando lo necesita. Los equipos con acceso ven cada problema y dónde está.

Reglas

Viva define y ajusta las reglas y el filtro de calidad para todos sus proyectos, sin pedir permiso a nadie.

Continuidad

Si cambia un proveedor, el control de calidad y su historial se quedan.

OPCIÓN A

En la nube: SonarQube Cloud

Servicio administrado por SonarSource, bajo una organización de Viva. Sin servidores que mantener.

OPCIÓN B

En infraestructura propia

En servidores y dominio de Viva, con una edición que revise cambios de código (Developer o superior). Viva la opera.

En ambas partimos de las reglas con las que trabaja hoy el equipo de Generic API. La configuración está incluida en el servicio (slide 12).

LA PROPUESTA · EL FILTRO DE CALIDAD

Un filtro automático que bloquea lo que no cumple

1

Compilar

¿El código compila? Si no, el cambio se detiene.

BLOQUEA
2

Pruebas unitarias

¿Pasan todas las pruebas unitarias? Una prueba unitaria rota detiene el cambio.

BLOQUEA
3

Análisis

¿Qué problemas nuevos hay? El detalle queda en el cambio, con el enlace a cada problema.

INFORMA
4

Filtro de calidad

¿Cumple el estándar de Viva? Si no, el cambio no se puede integrar.

BLOQUEA
Qué exige
el filtro
Pruebas unitarias que recorran al menos el 80 % del código nuevo · ningún defecto ni vulnerabilidad nueva · problemas de mantenimiento dentro del límite acordado · poco código duplicado (≤ 3 %).
Solo se exige al código nuevo de cada cambio: el código existente no frena el trabajo.

BENEFICIOS

Menos retrabajo, menos riesgo, más control

Viva Aerobus

  • Ningún cambio llega a la rama principal sin pasar el filtro de calidad.
  • Cada cambio nuevo llega con pruebas unitarias que se ejecutan siempre.
  • Los problemas dejan de acumularse: se controla lo nuevo sin frenar por lo existente.

Revisores

  • Dejan de corregir a mano lo que una máquina detecta.
  • Dedican su tiempo a diseño y negocio.
  • Un solo criterio de calidad, igual para todos los cambios.

Equipo de desarrollo

  • Ve cada problema y dónde está, desde el propio cambio.
  • Sabe si su cambio cumple antes de que lo revise una persona.
  • Menos devoluciones y menos idas y vueltas por cambio.

PRECONDICIONES

Lo que necesitamos para empezar

Decisión de Viva: dónde vive su herramienta de calidad, en la nube (SonarQube Cloud) o en infraestructura propia (slide 5).
SONAR

Punto de partida y destino

  • Acceso al SonarQube de Ezy (sonarqube.ezyflight.se) para descargar el perfil de reglas y el Quality Gate con los que trabaja hoy el equipo de Generic API: son el punto de partida.
  • Según la decisión: la organización de Viva en SonarQube Cloud, o el servidor, el dominio y la licencia (Developer o superior) del Sonar propio.
  • Un usuario administrador en el Sonar de Viva para configurar reglas, Quality Gate y el token del pipeline.
REPOSITORIO Y PIPELINE

GitHub

  • Permisos de administración en el repositorio para crear workflows de GitHub Actions y sus secretos.
  • Permiso para hacer obligatorios los checks del ruleset de master.
  • Runner ubuntu-latest para el job de calidad (hoy usa windows-latest, que no ejecuta contenedores Linux).
EQUIPO Y PROCESO

Acuerdos

  • Permiso para corregir los hallazgos de Sonar y escribir pruebas unitarias dentro de cada task.
  • Acuerdo de Viva y Ezy: un cambio que no pasa el filtro de calidad no se integra, y quién puede autorizar una excepción.
  • Un responsable de Viva, dueño de las reglas de calidad y del filtro para todos sus proyectos.

RESPONSABLE DE LOS CINCO ENTREGABLES
  • Sonar de Viva: instalar o configurar la instancia, migrar el perfil de reglas desde el Sonar de Ezy y crear el Quality Gate con cobertura ≥ 80 % del código nuevo.
  • Imagen Docker: construirla, versionarla y publicarla en el registro del repositorio.
  • Pipeline: configurar GitHub Actions con compilación, pruebas unitarias, cobertura y análisis apuntando al Sonar de Viva.
  • Bloqueo automático: hacer obligatorios los checks en el ruleset de master y verificar que un PR en rojo no se pueda mergear.
  • Lineamiento de pruebas unitarias: redactarlo con ejemplos sobre Generic API y la checklist del revisor.
