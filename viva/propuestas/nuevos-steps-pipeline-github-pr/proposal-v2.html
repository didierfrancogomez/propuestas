1. Lo que vemos, qué proponemos y qué gana

Revisamos el pipeline de PR de Generic API, su configuración en GitHub y la forma en que el equipo lleva una task hasta el merge. Estos son los puntos que vemos, la mejora que proponemos para cada uno y lo que gana Viva Aerobus con ella.

1Los controles no bloquean el merge
Lo que vemos

El pipeline compila y analiza, pero ningún check es obligatorio: un PR se puede mergear con la compilación o el Quality Gate en rojo. Solo la aprobación es obligatoria.

Qué proponemos

Volver obligatorios la compilación, las pruebas unitarias y el Quality Gate, con una activación gradual para no frenar al equipo (pasos 2 a 4).

Qué gana Viva Aerobus

A master solo llega código que pasó los controles obligatorios, salvo las excepciones que autoricen los administradores del repo.

2Las pruebas unitarias no se ejecutan
Lo que vemos

El repo tiene un proyecto de pruebas NUnit, pero el pipeline no lo ejecuta ni mide cobertura.

Qué proponemos

Ejecutar las pruebas en cada push y reportar la cobertura del código nuevo (paso 3).

Qué gana Viva Aerobus

Las regresiones que cubren las pruebas se detectan en el PR, en minutos, y no en QA o en producción.

3SonarQube corre, pero no se usa
Lo que vemos

El análisis publica su Quality Gate en cada PR, pero las reglas actuales del proyecto no permiten ajustar el código para resolver lo que reporta, así que sus hallazgos no se atienden.

Qué proponemos

Activar SonarQube como herramienta de apoyo para cada desarrollador: acordar que el equipo corrija los hallazgos del código nuevo, ajustar las reglas con el equipo y dar una sesión de uso (paso 4).

Qué gana Viva Aerobus

Cada desarrollador recibe en su propio PR lo que SonarQube detecta y lo corrige antes de la revisión, sin depender de un revisor central.

4El formato se corrige a mano
Lo que vemos

El estilo del equipo, definido en el perfil Ezy, se aplica a mano: depende de cada desarrollador y de que el revisor lo note.

Qué proponemos

Aplicar el perfil Ezy automáticamente en las líneas que toca cada PR (paso 1).

Qué gana Viva Aerobus

Los PRs dejan de devolverse por formato en todo lo que cubre el perfil, y el aprobador dedica su tiempo a la lógica.

5Las pruebas de servicios no corren en el PR
Lo que vemos

La colección de Postman no corre en el pipeline de PR, y la evidencia de las pruebas de cada task se arma a mano.

Qué proponemos

Ejecutar los casos de cada task contra la API del propio PR (paso 5), con lineamientos para que el equipo escriba pruebas con aserciones que verifiquen el resultado y se puedan repetir.

Qué gana Viva Aerobus

La evidencia se genera sola y es reproducible, y QA solo ejecuta los casos manuales.

6Cualquier persona puede aprobar cambios en pagos
Lo que vemos

El ruleset exige la aprobación de code owners, pero el repo no tiene archivo CODEOWNERS: la regla no tiene efecto, y cualquier persona con permiso de escritura aprueba cambios en el código sujeto a PCI.

Qué proponemos

Detectar cuándo un PR toca las rutas de pagos y exigir la aprobación del responsable de PCI (pasos 6 y 9).

Qué gana Viva Aerobus

Todo cambio en las rutas de pagos acordadas queda identificado y aprobado por su responsable.

7El PR no trae el contexto de la task
Lo que vemos

La plantilla del PR se completa a mano y ningún control la valida. El objetivo y la matriz de pruebas viven solo en Jira.

Qué proponemos

Traer al PR el objetivo y la matriz desde Jira, y validar que la plantilla esté completa y sea coherente con los cambios detectados (paso 7).

Qué gana Viva Aerobus

El aprobador tiene todo el contexto en el PR, y las declaraciones de cumplimiento y las release notes quedan listas.

8Copilot está habilitado, pero no revisa
Lo que vemos

La revisión de Copilot está habilitada en el repo, pero no revisa los PRs de forma automática. Nadie verifica si las pruebas cubren lo que pide la task.

Qué proponemos

Una revisión con IA en cada PR que valide, caso por caso, si las pruebas cubren los escenarios de la task y revise la lógica del cambio (paso 8). Reemplaza la revisión de Copilot.

Qué gana Viva Aerobus

El aprobador ve qué casos quedaron cubiertos, cuáles solo en parte y cuáles sin prueba, incluidas las pruebas que existen pero no verifican el resultado esperado.

En conjunto, el aprobador recibe PRs ya verificados y dedica su tiempo a lo que exige criterio: el diseño y las reglas de negocio.

Plazo
11 semanas con un ingeniero DevOps, llave en mano, con activación gradual para no frenar al equipo.
Qué necesitamos
Los accesos de la sección 6 desde la semana 0; un ambiente de pruebas al que llegue el pipeline y donde las pruebas puedan preparar sus propios datos; un responsable de PCI; un proveedor de IA aprobado; que el equipo pueda corregir los hallazgos de SonarQube en el código nuevo, y que el analista deje en cada task la matriz de pruebas con resultados esperados precisos.

Las secciones siguientes dan el detalle: cómo funciona hoy un PR (sección 2), cómo funcionaría con la propuesta (3), cómo se activa (4), cómo se mide (5) y el plazo, el alcance y las condiciones (6).

2. Estado actual

Este es el recorrido que hace hoy un PR hasta llegar a master, la rama principal del repo. Los términos técnicos se explican en el anexo.

PR
Se abre o se actualiza un pull request

El autor completa la plantilla del PR: impacto del release, PCI, privacidad y release notes. Ningún control automático valida su contenido.

Plantilla .github/pull_request_template.md.

3. Propuesta: de la task al merge

La propuesta cubre el recorrido completo de una actividad, desde que el analista deja lista la task en Jira hasta el merge. Primero, qué hace el pipeline en cada PR; después, qué hace cada actor y los lineamientos para las pruebas de servicios.

Qué hace el pipeline en cada PR

En cada push, el PR recorre estos pasos antes de llegar al aprobador. Cada paso indica qué se logra y si corrige solo, bloquea el merge hasta que alguien resuelva o solo informa.

PR
Se abre o se actualiza un pull request

Cada push al PR dispara el flujo completo.

1
Aplicar formateo de código Corrige
Objetivo

Que el código del PR cumpla el estilo Ezy del equipo sin intervención manual.

Beneficio

Los PRs dejan de devolverse por formato en todo lo que cubre el perfil Ezy, y el aprobador dedica su tiempo a la lógica.

2
Compilar la solución Bloquea
Objetivo

Garantizar que la solución compila antes de cualquier otra validación.

Beneficio

Un PR que no compila no puede mergearse a master.

3
Ejecutar pruebas unitarias Bloquea
Objetivo

Confirmar que el cambio no rompe comportamientos ya cubiertos por las pruebas y conocer la cobertura del código nuevo.

Beneficio

Las regresiones que cubren las pruebas se detectan en el PR, en minutos, y no en QA o en producción.

4
Ejecutar análisis de SonarQube Bloquea
Objetivo

Que SonarQube sea una herramienta real de apoyo para cada desarrollador: que le señale en su propio PR los bugs, las vulnerabilidades y las malas prácticas de su código nuevo, para corregirlos antes de la revisión.

Beneficio

Cada desarrollador recibe en su propio PR los hallazgos de las reglas de SonarQube y los corrige antes de la revisión, sin depender de un revisor central. El Quality Gate pasa a ser el criterio del merge y deja de depender de quien aprueba. Requiere que el equipo pueda corregir los hallazgos del código nuevo (sección 6).

5
Ejecutar pruebas de servicios Bloquea
Objetivo

Comprobar que la API del PR cumple los casos de prueba definidos en el ticket.

Beneficio

La evidencia se genera sola y es reproducible, y QA solo ejecuta los casos manuales. Requiere que los casos del ticket estén escritos en la colección de Postman, y la propuesta incluye los lineamientos para hacerlo (ver más abajo). Depende del supuesto del ambiente de pruebas (sección 6).

6
Detectar cambios en pagos (PCI) Corrige
Objetivo

Identificar cuándo un PR toca el código de pagos con tarjeta, que está sujeto a la certificación PCI, para que lo apruebe su responsable.

Beneficio

Todo cambio en las rutas de pagos acordadas queda identificado y requiere, en el paso 9, la aprobación del responsable de PCI.

7
Validar estructura del PR Corrige Bloquea
Objetivo

Que el PR llegue con su ticket, con el objetivo y la matriz de pruebas del ticket traídos desde Jira, y con la plantilla completa y coherente con los impactos detectados.

Beneficio

El autor no copia nada desde Jira: el PR tiene todo el contexto, con Jira como única fuente. El aprobador y la revisión con IA (paso 8) comparan el cambio contra lo pedido, y las declaraciones de cumplimiento y las release notes quedan listas.

8
Revisión con IA Informa IA
Objetivo

Validar, caso por caso, si las pruebas automatizadas cubren los escenarios de la task que el paso 7 dejó en el PR, y revisar la lógica del cambio.

Beneficio

El aprobador ve qué casos quedaron cubiertos, cuáles solo en parte y cuáles sin prueba, incluidas las pruebas que existen pero no verifican el resultado esperado. Son sugerencias: la decisión sigue siendo del aprobador.

9
Aprobación del PR Bloquea
Objetivo

Que el aprobador valide el diseño y las reglas de negocio antes del merge.

Beneficio

La revisión humana se concentra en lo que exige criterio, con el resumen de los pasos 1 a 8 a la vista.

✓
Merge a master

Solo es posible si el paso 9 aprobó y todos los pasos que bloquean están en verde.

Los pasos 6, 7 y 8 no dependen de la compilación: corren uno tras otro, en paralelo a los pasos 2 a 5. Los pasos 6 y 7 tardan segundos, así que el autor ve primero lo más rápido. Los bloqueos aplican a todos los PRs, salvo las excepciones que autoricen los administradores del repo. La sección 4 explica cómo se activan sin frenar al equipo. La revisión con IA del paso 8 reemplaza la revisión de Copilot, que hoy no se usa.

Quién hace qué: de la task al merge

Analista de la task→ Desarrollador→ PR (pipeline)→ Aprobador

Si el pipeline bloquea o el aprobador pide cambios, la actividad vuelve al desarrollador.

AN
Analista de la task

Deja la actividad lista para desarrollar, en Jira.

Redacta el objetivo y los criterios de aceptación de la task.

Arma la matriz de pruebas en la task: por cada caso, la entrada, el resultado esperado con valores precisos, los datos de prueba y si es automatizado o manual.

Marca la task como lista para desarrollo (TestCaseReady) cuando la matriz está completa. La matriz vive solo en la task.

DE
Desarrollador

Lleva la actividad hasta el PR.

Toma una task lista y crea la rama con su clave: feature/API-NNNN/...

Implementa el cambio y sus pruebas unitarias.

Agrega a la colección de Postman los casos automatizados de la matriz, con aserciones sobre el resultado esperado, siguiendo los lineamientos de pruebas de servicios.

Abre el PR y completa la plantilla: impacto del release, PCI, privacidad y release notes.

Corrige en su código nuevo los hallazgos que SonarQube le marque en el PR, antes de la revisión.

PR
PR (pipeline)

Verifica y completa el PR en cada push, sin intervención de nadie.

Ejecuta los pasos 1 a 8 del pipeline, que se detallan arriba: formatea, compila, prueba, analiza, ejecuta las pruebas de servicios, detecta cambios en pagos (PCI), trae el objetivo y la matriz desde Jira y ejecuta la revisión con IA.

Publica el resumen en el PR, adjunta la evidencia en Jira y asigna al aprobador.

Si un paso bloquea, el desarrollador corrige y hace push, y el pipeline vuelve a correr.

AP
Aprobador

Decide con toda la información a la vista.

Revisa el diseño y las reglas de negocio con el resumen, la evidencia y la validación de cobertura de la revisión con IA.

Si el PR toca pagos, la aprobación la da el responsable de PCI.

Aprueba o pide cambios. Si pide cambios, el PR vuelve al desarrollador.

✓
Merge a master

Con la aprobación y los pasos que bloquean en verde, se habilita el merge. QA solo ejecuta los casos manuales de la matriz.

Lineamientos para las pruebas de servicios

Para que el paso 5 compruebe lo que pide el ticket, las pruebas de Postman tienen que validar el resultado y poder repetirse. La propuesta incluye estos lineamientos para el equipo, con una plantilla, un flujo de ejemplo resuelto y una sesión de trabajo con los desarrolladores.

LineamientoQué asegura
Aserciones sobre el resultado de negocioQue la prueba falle si el valor devuelto no es el esperado, no solo si el servicio responde con error.
Validación del esquema de la respuestaQue se detecte un cambio en los tipos o en los campos obligatorios, aunque el valor parezca correcto.
Valores esperados tomados de la matrizQue cada caso de la task se ejecute con su entrada y su resultado esperado, y que el reporte diga qué caso pasó o falló.
Datos de prueba que la propia prueba prepara mediante llamadas a los servicios, en cada corridaQue la prueba no dependa de reservas que otra prueba modificó antes, y que varias corridas puedan ejecutarse a la vez sin pisarse.
Casos independientes entre síQue cada caso prepare su propio estado y se pueda ejecutar solo o en cualquier orden.
Sin credenciales dentro de la colecciónQue los datos sensibles vivan en el ambiente o en los secrets del pipeline.
Cada caso nombrado con la clave del ticket y su fila de la matrizQue el pipeline asocie cada prueba con su task y con su caso.

Tiempo del pipeline

Hoy el pipeline tarda una mediana de 6,8 minutos por push, porque solo compila y analiza. Los pasos nuevos suman tiempo, y cuánto depende de las pruebas del repo y del ambiente, así que no se proyecta una cifra. El tiempo se mide a medida que se activa cada paso, se informa al equipo y, si lo frena, se optimiza durante la estabilización.

5. Cómo mediremos que la verificación funciona

La propuesta automatiza la verificación de cada PR. No promete, por sí sola, mejorar la calidad del código: eso depende también de cómo el equipo escribe, prueba y revisa. Por eso los indicadores miden lo que el proyecto entrega: que la verificación ocurra en cada PR, que se respete y que no frene al equipo. La línea base se mide en la semana 1 con los datos de GitHub, y el reporte se entrega al cierre.

Supuesto: el ambiente de pruebas

El paso 5 depende de un ambiente que no controlamos. Por eso la propuesta lo declara como supuesto y lo verifica temprano, antes de comprometer el resto del trabajo en ese paso.

SupuestoEl pipeline puede acceder a un ambiente de pruebas de la API y de sus dependencias (dotREZ y demás integraciones), disponible en horario de trabajo, donde las pruebas preparan sus propios datos mediante llamadas a los servicios, por ejemplo creando la reserva que cada caso necesita. El desarrollador escribe esas llamadas como parte de sus casos.
Cómo se verificaEn la semana 3, con una prueba de concepto: desde el pipeline, un flujo completo que prepara sus datos por servicios, ejecuta el caso y valida el resultado.
Si no se cumpleEl paso 5 sale del alcance comprometido y, antes de continuar, se acuerda cómo seguir: ajustar el alcance y el precio, o habilitar el ambiente y mover el calendario. El resto de los pasos no depende de este supuesto.
Límite conocidoAlgunos escenarios necesitan estados que no se pueden crear por servicios, como tarifas o condiciones muy específicas. Esos casos quedan como manuales en la matriz.

Supuesto: el proveedor de IA

SupuestoViva Aerobus aprueba, a más tardar en la semana 4, un proveedor de IA y qué información del PR y del ticket se le puede enviar. El pipeline excluye los datos sensibles: PNR, nombres de pasajeros y datos de pago.
Cómo se verificaCon la aprobación por escrito del proveedor y de la política de datos, en la semana 4.
Si no se cumpleEl paso 8 sale del alcance comprometido y se ajustan el alcance y el precio. El resto del flujo no depende de la IA.
Límite conocidoLa IA puede equivocarse. Por eso informa y no bloquea, y su veredicto se calibra contra el del aprobador.

Criterios de aceptación

  • Los pasos 1 a 4 y 6 a 9 funcionan en el repo, y los que bloquean están configurados como obligatorios en el ruleset de master.
  • El paso 5 corre en cada PR en modo aviso, con los lineamientos aplicados en el flujo de ejemplo, si se cumple el supuesto del ambiente de pruebas.
  • El paso 8 corre en cada PR en modo informativo, con un reporte de calibración contra el criterio del aprobador en los 10 PRs de aceptación, si se cumple el supuesto del proveedor de IA.
  • El flujo corre sin intervención del ingeniero en 10 PRs reales consecutivos del equipo o, si en las últimas dos semanas del proyecto hay menos de 10, en todos los PRs de ese periodo.
  • La línea base y el reporte de los indicadores de la sección 5 están entregados.
  • Los lineamientos y la guía de operación están entregados, y las sesiones con el equipo, realizadas.

Condiciones

  • Viva Aerobus acuerda con los responsables del repositorio que el equipo pueda corregir, en el código nuevo de cada PR, los hallazgos que reporta SonarQube. Sin ese acuerdo, el paso 4 queda solo como aviso.
  • El analista deja en la task el objetivo, los criterios de aceptación y la matriz con resultados esperados precisos antes de marcarla como lista para desarrollo.
  • El equipo escribe los casos de cada ticket en la colección de Postman siguiendo los lineamientos. El valor del paso 5 depende de esta práctica.
  • Los costos de operación quedan a cargo de Viva Aerobus: minutos de GitHub Actions (en repos privados, los runners Windows consumen el doble), el consumo del proveedor de IA y, si se usa, la máquina del agente.

Fuera de alcance

  • Escribir los casos de Postman de cada ticket: siguen siendo parte del desarrollo de cada historia. Los lineamientos, la plantilla y el flujo de ejemplo sí están incluidos.
  • Corregir pruebas unitarias existentes que ya fallen hoy. Se reportan en la incorporación y se acuerdan aparte.
  • Proveer la máquina para el agente del pipeline y operarla después del traspaso (parches, monitoreo y respaldo).
  • Cambios en TeamCity o en el proceso de despliegue.
  • El soporte y el mantenimiento del pipeline después del traspaso. Se pueden acordar aparte.

7. Siguiente paso

Aprobar el alcance y el plazo, y enviar durante la semana 0 las solicitudes de acceso de la sección 6. El calendario de 11 semanas empieza cuando esté disponible el acceso de la semana 1.

Anexo: términos usados

TérminoQué significa
Task o ticketLa tarea o historia registrada en Jira, con su objetivo, sus criterios de aceptación y su matriz de pruebas. En este documento, los dos términos se usan como sinónimos.
PR (pull request)Solicitud para incorporar un cambio de código a la rama principal. Es donde el cambio se revisa y se aprueba.
MergeIncorporar el cambio del PR a la rama principal.
masterLa rama principal del repo, desde donde se despliega.
PushSubir cambios a una rama. Cada push al PR vuelve a correr el pipeline.
PipelineLa automatización que corre en cada PR, en GitHub Actions.
CheckEl resultado de un paso del pipeline, que aparece en el PR en verde o en rojo.
RulesetLas reglas de GitHub que protegen master, por ejemplo exigir aprobación o checks en verde.
CODEOWNERSArchivo que asigna responsables a partes del código. Con él, la aprobación del responsable se vuelve obligatoria.
PCIEstándar de seguridad para pagos con tarjeta (PCI DSS). Los servicios de pago de Viva Aerobus están certificados bajo este estándar, así que los cambios en ese código requieren una revisión especial.
SonarQube y Quality GateLa herramienta que analiza el código y el umbral de calidad que el código nuevo debe cumplir.
CoberturaPorcentaje del código que ejecutan las pruebas.
PostmanLa herramienta donde el equipo define las pruebas de los servicios de la API. El pipeline las ejecuta sin interfaz.
AserciónUna comprobación dentro de una prueba, por ejemplo que un campo tenga el valor esperado.
IA (modelo de lenguaje)Modelo que interpreta texto y código. En este flujo valida si las pruebas cubren los escenarios de la task y revisa la lógica del cambio. Informa; no bloquea.
CalibraciónComparar los resultados de la IA con el criterio del aprobador en PRs reales, para saber cuánto confiar en ellos.
Perfil EzyLas reglas de formato de código del equipo, definidas en la solución.
Agente del pipeline (runner)La máquina que ejecuta los pasos del pipeline.
SecretsCredenciales guardadas de forma segura en GitHub para que el pipeline las use.
GitHub AppLa identidad técnica con la que el pipeline sube el commit de formateo.
PNREl localizador de una reserva. En pruebas, reservas de ejemplo del ambiente de test.
dotREZEl sistema de reservas del que depende la API.
TestCaseReadyEtiqueta de Jira que indica que la task tiene su matriz de pruebas completa.
