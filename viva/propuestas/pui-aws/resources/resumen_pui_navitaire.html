Integración PUI ↔ Viva (AWS + Navitaire)

Resumen del documento "Diseño Técnico PUI AWS Navitaire" v1.0 (14 sep 2026). Es un borrador para cotizar.

De qué trata

Viva debe exponer APIs para que la PUI le envíe casos identificados por CURP. Viva busca esa CURP en Navitaire, donde está guardada como Travel Document, y reporta las coincidencias a la PUI en 3 fases: datos básicos, histórico de hasta 12 años y búsqueda continua hasta que el caso se desactive. Todo se construye en AWS y es serverless.

PUI: la Plataforma Única de Identidad del gobierno de México, vinculada a la búsqueda de personas desaparecidas. Las instituciones obligadas reciben CURPs y deben reportar a la autoridad cualquier rastro que encuentren, como vuelos y reservas.
Navitaire: el PSS (Passenger Service System) de Amadeus, que usan aerolíneas low-cost como Viva. Ahí viven las reservas, los pasajeros, los segmentos y los documentos de viaje. Aquí se usará solo vía API, sin ODS ni RaaS.

Diseño propuesto

PUI→ WAF + API Gateway
JWT Cognito + scopes→ Lambda API
activar / prueba / desactivar→ DynamoDB
casos, matches, cursores+ SQS→ Lambda Workers
fases 1, 2 y 3⇄ Navitaire API
adaptador
EventBridge
cron de la fase 3→ SQS notif. + DLQ→ Lambda Notifier→ PUI
/notificar-coincidencia, /busqueda-finalizada, /reportes

Transversal: KMS (CURP cifrada + hash), Secrets Manager, CloudWatch/CloudTrail, IaC (CDK o Terraform) y CI/CD. Se sugiere Step Functions para orquestar la fase 1, la fase 2 y el cierre con /busqueda-finalizada.

Dudas abiertas para estimar

  1. Navitaire: ¿la API (New Skies / dotREZ) permite buscar por número de Travel Document? ¿Con qué endpoint y versión? Si no lo permite, se cae el diseño.
  2. Navitaire: ¿qué código de tipo de documento corresponde a CURP? ¿Se captura la CURP hoy en las reservas? Sin captura no habrá coincidencias.
  3. Navitaire: ¿hay 12 años de histórico disponibles por API? ¿Qué rate limits, sesiones y costo por llamada tiene?
  4. Fase 3: ¿existe una búsqueda incremental o eventos? Si no, hay que hacer polling por cada caso activo, lo que afecta volumen y costo.
  5. PUI: ¿hay un contrato oficial (OpenAPI/manual), un sandbox, credenciales y una IP fija? ¿Exigen la ruta literal /login?
  6. Datos: falta la matriz de campos permitidos para enviar a la PUI (aprobación de Legal) y la regla para reportar múltiples coincidencias.
  7. Volumen: ¿cuántos casos activos se esperan y qué SLA de respuesta exige la PUI?
  8. Entorno: ¿cuentas AWS y VPC existentes, qué herramienta de IaC y CI/CD, qué lenguaje, y cuántos ambientes (dev/qa/prod)?
  9. Alcance del proveedor: ¿quién ejecuta el pentest y DAST? ¿Incluye soporte post-producción u operación?

Orden de magnitud (preliminar)

Equipo de unos 3–4 personas (arquitecto/líder, 2 backend, QA) durante 10–14 semanas. El rango depende sobre todo de las dudas 1, 3 y 4 sobre Navitaire. Se recomienda un spike de 2 semanas sobre la API de Navitaire antes de cerrar la cifra.
