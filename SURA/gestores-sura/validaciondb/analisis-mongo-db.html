MongoDB en la solución de gestores: análisis

Si vale la pena usar MongoDB en la implementación de los gestores y la torre de control, qué ganaría y qué costaría la solución, y qué otras bases de datos del ecosistema Microsoft pueden competir con ella y ganarle.

SURA Colombia · Transformación prestación y reclamaciones, MVP de autorizaciones de salud

Elaborado por Tech and Solve para SURA · Octubre de 2026

Se apoya en el alcance del MVP de gestores ya dimensionado, en los lineamientos AI First de la organización y en la documentación oficial de MongoDB y de Microsoft. Cada afirmación sobre un producto lleva su enlace en el mismo bloque.

La respuesta corta

Nuestra recomendación

Sí al modelo documental y a la API de MongoDB; no a introducir MongoDB Atlas como producto nuevo en el MVP. La memoria de los agentes y los estados propios de los gestores se quedan en el servicio documental de Azure que el lineamiento ya fija, se programan con PyMongo detrás del Memory Manager, y la decisión de pasar a Atlas queda abierta y barata para cuando aparezca un motivo que hoy no está escrito.

Las cuatro preguntas del encargo, en una línea cada una:

  1. ¿Vale la pena? MongoDB solo compite por dos de los siete lugares donde la solución guarda datos, y en esos dos el lineamiento ya eligió un servicio compatible con su API. Cambiar a Atlas suma un proveedor, un contrato y un plano de gestión aparte para ganar capacidades que el MVP todavía no pide.
  2. Ventajas. Es el motor original y no una emulación: compatibilidad total, cifrado consultable para datos clínicos, búsqueda vectorial y de texto en la misma base, checkpointer oficial de LangGraph, y portabilidad entre nubes. Se contrata desde el portal de Azure.
  3. Desventajas. Contradice el stack vigente, que declara Cosmos DB obligatorio y deja a Atlas como «futuro, evaluar contra Cosmos»; duplica la búsqueda vectorial que Azure AI Search ya estandariza; parte el soporte en dos fabricantes, y obliga a clústeres dedicados para tener red privada e identidad administrada.
  4. Quién compite y gana. Azure DocumentDB si se quiere conservar la API de MongoDB, Azure Cosmos DB for NoSQL si se prioriza la integración con el ecosistema agéntico de Microsoft, y Azure Database for PostgreSQL para las reglas versionadas y la configuración, que tienen forma relacional y ya tienen motor en el stack.

Qué se está decidiendo en realidad

La pregunta «¿usamos MongoDB?» tiene dos lecturas, y conviene separarlas porque tienen respuestas distintas.

MongoDB como API y modelo de datos
Documentos JSON, el lenguaje de consulta de MongoDB y sus drivers. Esto ya está decidido: la arquitectura de implementación de agentes fija el Memory Manager con PyMongo sobre «Azure Cosmos DB con API Mongo» para la memoria de largo plazo (AI First, página 5684887560).
MongoDB Atlas como producto
El servicio administrado de MongoDB Inc., que en Azure se aprovisiona como integración nativa de Azure, desarrollada y gestionada en conjunto por Microsoft y MongoDB. Esto es lo que está en discusión, y el stack v0.5 ya lo tiene anotado como «Futuro (evaluar vs Cosmos)».
Un punto que conviene cerrar antes que cualquier otro

«Cosmos DB con API Mongo» hoy nombra dos servicios distintos. La propia documentación de Microsoft recomienda, a quien quiera usar el lenguaje de consulta de MongoDB, considerar Azure DocumentDB, que es el nuevo nombre del antiguo Cosmos DB for MongoDB vCore, y deja la variante por unidades de solicitud para otros escenarios. Antes de comparar contra Atlas hay que saber contra cuál de los dos se está comparando.

Qué datos maneja la solución, y dónde puede entrar MongoDB

El MVP dimensionado son cuatro frentes —Gestor de Solicitud, Gestor de Evaluación, Gestor de Coordinación en su nivel 1, y las capas 1 y 2 de la torre de control— sobre la plataforma habilitadora. Recorriendo la vista de tecnología y el lineamiento, la solución guarda datos en siete lugares. Cada uno tiene una forma distinta, y esa forma decide qué motor le sirve.

1¿Vale la pena usar MongoDB Atlas?

Para el MVP, no como producto nuevo. Como API y modelo de datos, ya se está usando.

El criterio que aplicamos es el mismo que usamos en el resto de la propuesta: una pieza entra cuando cambia una decisión o resuelve un problema que hoy no tiene respuesta. Mirado así:

  • No resuelve un problema abierto del MVP. Los riesgos del dimensionamiento son el motor de extracción documental, el producto del bus, el nivel de autonomía de cada agente y las API del core. Ninguno se mueve con el motor de la memoria.
  • Compite por dos de siete lugares, y en esos dos el lineamiento ya tiene un servicio con la misma API. El trabajo de desarrollo es casi el mismo con cualquiera de ellos: el Memory Manager con PyMongo no cambia.
  • Lo que sí cambia es lo que no se ve en el código: un contrato con otro fabricante, un plano de gestión aparte del portal de Azure, el encaje con la separación de suscripciones entre dominio de agentes y dominio de información que exige el lineamiento de infraestructura, y la aprobación de una excepción al stack vigente.
  • Es una decisión de dos vías si se diseña bien. Si el acceso a la memoria queda detrás del Memory Manager y se programa contra la API de MongoDB, pasar después a Atlas es cambiar una cadena de conexión y migrar datos, no reescribir agentes. Eso permite no decidirlo hoy sin cerrarse la puerta.
Lo que se podrá afirmar con esta decisión

Que la solución usa el modelo documental donde le sirve, que la memoria y los estados de los gestores pueden moverse de motor sin tocar los agentes, y que ninguna pieza del MVP queda fuera del stack que la organización ya aprobó.

2Qué ventajas tendría MongoDB Atlas

Son reales, y algunas pesan en salud. Las presentamos según la documentación del fabricante, como práctica documentada y no como norma.

V1Es el motor original, no una capa de compatibilidad
Qué es
Atlas ejecuta el servidor de MongoDB. Los servicios de Azure son compatibles con su protocolo pero no lo ejecutan: Microsoft declara que Azure DocumentDB no corre el servidor de MongoDB y que su compatibilidad es del 99,03%.
Por qué importa
Las librerías que mantiene MongoDB, como el checkpointer de LangGraph, se prueban contra su motor. Con Atlas no hay que verificar ese 0,97% restante.
V2Cifrado consultable para datos clínicos
Qué es
Queryable Encryption cifra campos en el cliente y permite consultarlos cifrados; la documentación declara consultas por igualdad, rango, prefijo, sufijo y subcadena.
Por qué importa
El Gestor de Solicitud custodia temporalmente la historia clínica y la orden médica. Es la ventaja con más peso en este dominio, y la única que ningún competidor de este análisis ofrece igual. Antes de apoyarse en ella hay que confirmar en su página de compatibilidad qué tipos de consulta están liberados para la versión y el driver que se usen.
V3Memoria de LangGraph mantenida por el fabricante
Qué es
MongoDB documenta la integración con LangGraph y publica el paquete langgraph-checkpoint-mongodb para persistir checkpoints, con expiración configurable.
Por qué importa
El runtime agéntico del lineamiento es LangGraph en Python, y la memoria operacional obligatoria son justamente los checkpoints del grafo.
V4Búsqueda vectorial, de texto e híbrida en la misma base
Qué es
Atlas Vector Search y la búsqueda híbrida con $rankFusion operan sobre los mismos documentos operacionales.
Por qué importa
Sirve para la memoria semántica de largo plazo y para la capa de duplicidad, que busca a qué solicitud se parece una nueva. Para el conocimiento de RAG no la recomendamos: ese lugar ya es de Azure AI Search.
V5Se contrata y se opera desde Azure, con red privada e identidad administrada
Qué es
Se suscribe desde el portal o el Marketplace de Azure. Soporta Azure Private Link y federación de identidad de carga con identidades administradas de AKS, lo que encaja con Managed Identity del lineamiento.
Por qué importa
Si la oferta tiene la marca «Azure benefit eligible», la compra por el portal abona al compromiso de consumo de Azure. Es algo que conviene confirmar con el equipo de compras de SURA, no suponerlo.
V6Portabilidad, eventos y talento
Qué es
El mismo servicio corre en más de cuarenta regiones de Azure y en otras nubes. Tiene change streams para publicar cada cambio de estado, transacciones multi-documento y validación de esquema.
Por qué importa
El lineamiento ya contempla modelos en otras nubes y un gateway de negocio en GCP. Los change streams sirven para el patrón de un evento por cada cambio de estado. Y es la base documental con más desarrolladores formados en el mercado, una opinión nuestra que conviene contrastar con el equipo.
3Qué desventajas tendría

Casi ninguna es técnica. Son de gobierno, de ecosistema y de operación.

D1Va contra el stack que la organización ya aprobó
El hecho
El stack v0.5 declara Cosmos DB obligatorio para la memoria conversacional y operacional, «ya en uso», y registra a MongoDB Atlas como «Futuro (evaluar vs Cosmos)», sin riesgo mitigado (AI First, página 5900140571). La arquitectura de implementación repite Cosmos DB como Memory Layer (página 6243680318).
Consecuencia
Usarlo en el MVP es pedir una excepción al lineamiento, con su registro de decisión y su aprobación. Un MVP con dependencias críticas abiertas no es el mejor lugar para abrir una más.
D2Duplica capacidades que el ecosistema ya tiene estandarizadas
El hecho
Azure AI Search es el estándar corporativo para búsqueda vectorial e híbrida, y el riesgo que el lineamiento dice mitigar con él es la «fragmentación de soluciones vectoriales».
Consecuencia
La ventaja V4 solo vale si se acota a la memoria y a la duplicidad. Si Atlas termina indexando conocimiento, el ecosistema queda con dos motores vectoriales y dos versionados de embeddings.
D3Un fabricante más, y un plano de gestión aparte
El hecho
La integración nativa resuelve el aprovisionamiento y la facturación, pero la organización, los proyectos, los usuarios y las alertas de Atlas se administran en Atlas. El soporte queda repartido entre MongoDB y Microsoft.
Consecuencia
Hay que definir cómo encaja en la separación de suscripciones entre dominio de agentes y dominio de información, y verificar con el equipo de seguridad qué cobertura tienen sus herramientas de postura, políticas y catálogo sobre un servicio de tercero. Esa verificación tiene dueño y plazo propios.
D4Lo que se necesita exige clúster dedicado
El hecho
El endpoint privado está disponible desde M10 y no en los clústeres gratuitos ni Flex. La identidad administrada exige M10 con MongoDB 7.0.11 o superior.
Consecuencia
Cada ambiente, desarrollo, pruebas y producción, paga un clúster encendido todo el tiempo. Cosmos DB cobra por unidades de solicitud y admite modalidad sin servidor, que para un MVP con carga que crece de a poco suelen salir más baratas. El costo exacto depende del tamaño y no lo estimamos aquí.
D5Menos integración con el resto del ecosistema Microsoft
El hecho
El espejo de Cosmos DB hacia Fabric es nativo, sin ETL y sin consumir capacidad transaccional, pero solo para Cosmos DB for NoSQL. Para Atlas existe una solución del fabricante sobre open mirroring. El Agent Service de Foundry, en su configuración estándar, guarda sus hilos en Cosmos DB for NoSQL propio.
Consecuencia
Hoy pesa poco, porque el lineamiento usa LangGraph en AKS y Databricks sobre ADLS. Pesa más si la organización se mueve hacia los servicios gestionados de Microsoft.
Lo que no es una desventaja

La residencia del dato es igual en todos los casos. Ni Atlas ni los servicios de Azure tienen región en Colombia; en Suramérica Atlas ofrece las mismas regiones de Azure, Brazil South, Brazil Southeast y Chile Central. La transferencia internacional de datos personales es la misma conversación con cualquier motor. Tampoco lo es la licencia: la SSPL afecta a quien ofrece MongoDB como servicio a terceros, no a quien consume Atlas.

4Qué otras bases de datos compiten, y dónde ganan

Sobre el stack de Microsoft y su nube, tres alternativas le ganan a Atlas en el MVP, cada una en un lugar distinto.

AAzure DocumentDB, antes Cosmos DB for MongoDB vCore
Gana si se quiere conservar la API de MongoDB
Dónde gana

Mantiene PyMongo y el lenguaje de consulta de MongoDB, como pide la arquitectura de implementación, sin salir de un servicio de primera parte de Azure.

  • Es la recomendación de Microsoft para cargas que usan el lenguaje de MongoDB, y declara 99,03% de compatibilidad por protocolo y BSON.
  • Corre sobre DocumentDB, motor abierto con licencia MIT gobernado por la Linux Foundation: da portabilidad entre nubes sin depender de un fabricante.
  • Incluye búsqueda vectorial sin costo adicional, útil para memoria semántica y duplicidad.

Dónde pierde

No es el motor original: el checkpointer de LangGraph y cualquier operador avanzado se verifican antes de comprometerse, y el cifrado consultable de V2 no es una capacidad que su documentación declare.

BAzure Cosmos DB for NoSQL
Gana en integración con el ecosistema agéntico de Microsoft
Dónde gana

Es la base que Microsoft documenta para memoria de agentes, la que usan sus propios servicios agénticos y la única con espejo nativo a Fabric.

  • Guía oficial de memoria de agentes con particionado por inquilino e hilo, TTL, búsqueda vectorial, de texto e híbrida.
  • El paquete langchain-azure-cosmosdb trae checkpointer de LangGraph, almacén de memoria larga y caché semántica, con identidad administrada de Entra ID.
  • Búsqueda vectorial con DiskANN, texto completo con BM25 y búsqueda híbrida; change feed para publicar cambios de estado; TTL nativo; distribución multi-región.

Dónde pierde

Su API es otra. El Memory Manager con PyMongo que fija la implementación v1.1 se reescribe contra otro SDK, y eso es cambiar el lineamiento por el otro lado.

CAzure Database for PostgreSQL, servidor flexible
Gana en reglas, configuración y todo lo que tiene forma relacional
Dónde gana

Ya está en el stack como base transversal del plano de control. Usarla para lo relacional evita sumar un motor.

  • Las reglas duras versionadas con vigencia y autor, los umbrales por tipo de caso, los techos de autonomía y los pesos del ranking de prestadores son filas con historia, y la negación se sustenta en ellas: necesitan integridad y consulta por vigencia más que esquema flexible.
  • Con pgvector cubre vectores si hiciera falta, y LangGraph tiene checkpointer propio para PostgreSQL.

Dónde pierde

Para el documento del caso con servicios hijo y eventos que llegan desordenados, el modelo documental es más natural. No la proponemos para la memoria.

5Recomendación y secuencia

Una decisión firme para el MVP y una puerta abierta para después, con criterio explícito para abrirla.

  1. Precisar «Cosmos con API Mongo» como Azure DocumentDB para la memoria de los agentes y los estados propios de los gestores. Conserva PyMongo, conserva el lineamiento y sigue la recomendación vigente de Microsoft para el lenguaje de MongoDB.
  2. Hacer una prueba corta de compatibilidad en el arranque: el checkpointer de LangGraph de MongoDB, las transacciones que use el cambio de estado y la expiración por tipo de memoria, contra Azure DocumentDB. Si algo falla, la alternativa de primera parte es Cosmos DB for NoSQL con su checkpointer.
  3. Dejar la memoria detrás del Memory Manager, sin consultas al motor desde los nodos del grafo. Es lo que vuelve reversible esta decisión.
  4. Llevar las reglas, umbrales, techos y pesos a PostgreSQL Flexible, con Redis como caché de lectura, que ya es lo que propone la vista de tecnología.
  5. No usar vectores fuera de Azure AI Search salvo para memoria semántica y duplicidad, y registrarlo así para que no se lea como un segundo estándar vectorial.
  6. Registrar la decisión en el formato de decisiones de arquitectura de la organización, con la condición de revisión de la sección siguiente.
Efecto en el dimensionamiento

Ninguno de los seis pasos agrega requisitos al MVP: el Memory Manager ya está contado. Elegir Atlas tampoco cambia el desarrollo, pero suma una habilitación —contrato, red privada, identidad, encaje en suscripciones— que hoy no está en los números y cuyo plazo declara su dueño.

Cuándo sí elegiríamos MongoDB Atlas

Si se cumple cualquiera de estas condiciones, Atlas pasa de ser una excepción a ser la mejor opción, y el cambio cuesta poco gracias al paso 3:

Cifrado consultable exigido
Seguridad o jurídica piden que los campos de la historia clínica estén cifrados en el almacén operacional y se puedan consultar así. Es la ventaja que ningún competidor iguala.
La prueba de compatibilidad falla
Azure DocumentDB no soporta algo que la memoria o los estados necesitan, y Cosmos DB for NoSQL no es aceptable por el cambio de SDK.
Existe una relación con MongoDB
SURA ya tiene contrato, soporte o equipos operando Atlas en otra línea de negocio. Entonces el fabricante adicional ya está y D3 pierde peso.
Estrategia multinube explícita
La organización decide operar el mismo dominio de agentes en más de una nube. DocumentDB también es portable, pero Atlas lo es como servicio gestionado.

Preguntas para el equipo

Cerrarlas antes del sprint 1 evita decidir esto por omisión.

Para conversar

¿Qué motivó plantear MongoDB: una capacidad concreta, una relación existente con el fabricante, o la familiaridad del equipo con la API? La respuesta decide cuál de las cuatro condiciones de arriba aplica.

  • Cuando el lineamiento dice «Cosmos DB con API Mongo», ¿se refiere a la variante por unidades de solicitud o a Azure DocumentDB? ¿Qué usa hoy Insuregent, que el diagnóstico cita como antecedente?
  • ¿Exige seguridad o jurídica cifrado a nivel de campo para la historia clínica que custodia el Gestor de Solicitud?
  • ¿La oferta de MongoDB Atlas en el Marketplace abona al compromiso de consumo de Azure de SURA?
  • ¿Quién aprueba una excepción al stack v0.5, y con qué formato de decisión?
  • ¿Hay planes de usar el Agent Service de Foundry o Fabric sobre la memoria de los agentes? Si los hay, Cosmos DB for NoSQL gana peso.
